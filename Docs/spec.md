## 2. サイト構成

- ポータルトップ（`index.html`）にゲーム一覧をカード形式で表示し、カードをクリックすると各ゲーム画面（`gomoku.html` / `gogo-shogi.html` / `tictactoe.html` / `otrio.html` / `yonmoku.html` / `gobblet.html`）に遷移する。カードには「CPU対戦」「オンライン対戦」のタグを表示する。
- 各ゲーム画面は「対戦相手選択（CPU対戦/オンライン対戦/ルール説明） → （CPU対戦なら難易度選択 →）対局画面 → 結果バナー（もう一度対局する / ポータルトップへ）」という共通の画面遷移パターンに従う。
- ヘッダーは全ページ共通で、ゲーム画面ではポータルトップへ戻る導線を表示する。

## 3. デザインシステム

要求仕様書のヒアリングに基づき「モダン・ミニマル」路線を採用。

- 背景: チャコール系（`#1c1f26`）、カード面: `#262a33` + 細いボーダー
- アクセントカラー: ゲームごとに切り替え（五目並べ=レッド`#ef4444`、五五将棋=アンバー`#e8a33d`、〇×ゲーム=ブルー`#4d96ff`、オートリオ=パープル`#c77dff`）。当初五目並べはエメラルド`#3ddc97`だったが、後述の「オンライン対戦」タグの統一色（ティール系`#2dd4bf`）と近すぎたためレッドに変更した。
- ポータルカードの「CPU対戦」「オンライン対戦」タグはゲームごとのアクセント色に合わせず、全ゲーム共通の色（CPU対戦=ニュートラルなグレー、オンライン対戦=ティール`--color-accent-online: #2dd4bf`）で統一している。
- ポータルカードのアイコンはゲームごとにSVGを個別に用意している。オートリオ・ゴブレット・ゴブラーズは当初どちらも「格子の中に大中小の四角形を同心状に重ねる」モチーフで似通っていたため、ゴブレット・ゴブラーズ側を「駒が別マスへ動く矢印」＋「移動先で相手の小さい駒に被さる」という固有メカニクス（移動＋被覆）を表現するデザインに変更し、視覚的に差別化した（カード説明文も「駒を被せて相手を隠し、動かして入れ替える陣取りゲーム。」に変更）。変更前にArtifactでラフ案を3パターン提示し、ユーザーが選んだ案を採用する流れで実施した。
- 角丸: 8px、フラットでシャープなカード形状
- フォント: ニュートラルなゴシック体一本（`Hiragino Sans` / `Yu Gothic` 等のシステムフォントスタック）
- 今後ゲームが増えてもカードを追加するだけで一覧に反映される配列駆動の構造

## 4. 共通UI仕様

- **難易度選択**: 弱・中・強の3段階を共通コンポーネントで提供。全ゲームで見た目・操作感を統一。
- **結果バナー**: 勝ち/負け/引き分けをメッセージ付きで表示し、「もう一度対局する」（難易度選択に戻る）「ポータルトップへ」の導線を提供。当初は全画面オーバーレイの結果モーダルだったが、詰み等の最終盤面が隠れて見えなくなる問題があったため、対局画面のコンテナ先頭に挿入する非モーダルの「結果バナー」に変更した（盤面・持ち駒表示は常に完全に見える）。勝ち=緑、負け=赤、引き分け=ニュートラルに色分け。
- **オンライン対戦ロビーの「ルームを作成する」UI**: 「手番」「公開設定」をそれぞれトグルボタンで選択したうえで、最後に単一の「ルームを作成」ボタンを押す方式（全6ゲーム共通）。当初は公開/非公開ボタンを押した瞬間にルームが作成される仕様だったが、「先手/後手は選ぶだけなのに公開/非公開は押すと即実行される」という非対称なUXが分かりにくいという指摘を受けて、設定→実行を分離する形に変更した。あわせて、設定項目ごとのボタン列が隙間なく密着して見えていた問題も、項目間にラベルと余白を追加して解消した。
- **ヘッダー**: ポータルトップへの導線を常時表示。

## 5. ゲーム1: 五目並べ（Gomoku）

要求仕様書の記載どおり実装。差分・確定事項は以下。

- 盤面15×15、5つ以上連続で勝利、禁じ手なし。既存Firestore実装は流用せず、盤面状態はブラウザ内Stateで完結。
- プレイヤーは黒（先手）固定、CPUは白（後手）固定。
- 難易度ごとのAI実装（実装時に確定した具体的な方針）:
  - **弱**: 「自分が置けば5連になる手」を必打、「相手が次に置けば5連になる手」を必ず阻止。それ以外は候補手（既存石の周農2マス以内）からランダム選択。
  - **中**: 連続数・両端の空き具合をスコア化する評価関数による1手先読み（貪欲法）。
  - **強**: 同評価関数＋ミニマックス法（αβ枝刈り）で4手先読み。候補手は既存石の周辺2マス以内、評価スコア上位8手に絞って探索空間を抑制。
### 4.4 オンライン対戦（Phase 2）

要求仕様書の付録（`gomoku_requirements.md`）はルームURL共有方式を想定していたが、実装時の相談により以下の方式に変更して実装した。

- ルームURLでの共有は行わない。**ルーム一覧から参加**するか、**ルーム番号（6文字コード）を入力して参加**するかのいずれか。
- ルーム作成時に**公開/非公開**を選択できる。公開ルームのみ一覧（Firestoreのリアルタイムクエリ）に表示され誰でも参加可能。非公開ルームは一覧に出ず、番号を知っている人だけが参加できる。
- プレイヤー名の入力は任意。ブラウザへの記憶（localStorage）は行わない。未入力の場合は「先手」「後手」と表示する。
- 対局が放置された場合に備え、ルームは作成から**3時間でFirestoreのTTL機能により自動削除**される（要Google Cloud ConsoleでのTTLポリシー設定、`Docs/README.md`参照）。
- 盤面ロジック（`checkWin`, `isBoardFull`, 盤面生成）はCPU対戦と共通のものをそのまま再利用。着手はFirestoreの`runTransaction`で「手番か」「空きマスか」を再確認してから書き込み、勝敗判定もクライアント側で行う（サーバーサイドロジックは持たない）。
- データモデル: `games/{roomId}`（`board`はFirestoreがネスト配列を扱えないため225要素のフラット配列で保存し、アプリ内では15×15の2次元配列に変換して扱う。詳細は`Docs/design.md`参照）。
- 五五将棋にも同じ設計思想でオンライン対戦を実装済み（詳細は6.1節）。

## 6. ゲーム2: 五五将棋（ごごしょうぎ / Minishogi）

要求仕様書5章の内容をそのまま実装。特に複雑なルールは実装時にユニットテストで正しさを担保した。

- 5×5盤、6種12枚の駒（王将/玉将・飛車・角行・銀将・金将・歩兵）、桂馬・香車なし。
- 成り: 敵陣は最も奥の1列のみ。王将・玉将・金将は成れない。飛車→竜王、角行→竜馬、銀将→成銀、歩兵→と金。
- 禁止事項: 二歩、打ち歩詰め、行き所のない駒（最奥段への歩打ち等）を実装・テスト済み。
- 勝敗判定: 詰み判定を実装。**千日手（同一局面4回出現）は先手の負け**、連続王手の千日手は王手をかけ続けた側の負け、という五五将棋特有ルールを実装（局面キー＋着手履歴から判定）。持将棋の判定ロジックは要求仕様書どおり未実装（投了ボタンで終局を促す）。
- 投了ボタンを実装。CPUは評価値が著しく劣勢（駒得換算で概ね飛車を失う規模以上）と判断した場合に投了する。
- プレイヤーは先手（王将）固定、CPUは後手（玉将）固定。
- 難易度ごとのAI実装（実装時に確定した具体的な方針）:
  - **弱**: 合法手（王手放置となる手は合法手生成の時点で除外済み）からランダム選択。
  - **中**: 駒得＋簡易玉安全度評価によるミニマックス（αβ枝刈り）で3手読み。
  - **強**: 駒得＋玉安全度＋盤面支配（可動域）を含む評価関数によるミニマックス（αβ枝刈り）で4手読み。
- 画面構成: 5×5盤面、持ち駒表示（先手・後手それぞれ）、手番・王手表示、成り選択ポップアップ（敵陣に関わる手を指した際、成る/成らないの両方が選べる場合のみ表示）。
- 駒の表示は漢字1文字（王/玉/飛/角/銀/金/歩/竜/馬/全/と）。後手の駒は視認性のため180度回転して表示。

### 6.1 オンライン対戦（Phase 2）

五目並べのオンライン対戦（4.4節）と同じUI・運用方針（ルーム一覧＋番号参加、公開/非公開、名前任意、3時間TTL）をそのまま踏襲している。データが複雑になる分、以下の点が異なる。

- Firestoreのコレクションは`shogiGames`（五目並べの`games`とは別）を使用。スキーマが大きく異なるため分離した。
- 盤面（5×5）に加えて**持ち駒（hand）**もFirestoreに同期する。取った駒は即座に相手側の持ち駒欄から消え、自分側に反映される。
- **成り/不成りの選択**はCPU対戦と共通のポップアップ（`src/games/gogo-shogi/ui/promotionPrompt.ts`）をそのまま使用。ローカルで選択を確定させてから着手として送信するため、追加の同期は不要。
- **千日手判定**のため、着手履歴（`HistoryEntry[]`）をルームドキュメントに保持し、既存の`checkRepetition`（ロジック層で実装・テスト済み）をそのまま利用する。
- 決着理由（`winReason`）として「詰み」「投了」「千日手」「連続王手の千日手」の4種類を管理し、結果表示のメッセージを出し分ける。
- プレイヤーは先手（王将）固定、参加者が後手（玉将）固定（CPU対戦と同じ役割分担）。

## 7. ゲーム3: 〇×ゲーム（三目並べ）

`Docs/todo.md`の要望により追加。要求仕様書には記載がないため、既存2ゲームと同じ設計思想（難易度選択→対局→結果、ルール説明画面）で新規に仕様化した。

- 3×3盤、2人が交互に○×を置き、縦・横・斜めのいずれかに自分の記号を3つ連続で並べたら勝ち。禁じ手なし。盤面が埋まって決着しなければ引き分け。
- プレイヤーは○（先手）固定、CPUは×（後手）固定。
- 難易度ごとのAI実装:
  - **弱**: 即勝ち・即阻止を優先し、なければランダム。
  - **中**: 深さ2のミニマックス＋簡易評価関数。
  - **強**: 深さ9（盤面を使い切るまで）のフルミニマックス＋αβ枝刈り。3×3は状態数が小さいため事実上の完全読みとなり、最善手を指し続ければ引き分け以下にはならない（実装時にブラウザで検証済み）。
- 投了ボタン・ルール説明画面あり。

### 7.1 オンライン対戦

五目並べ・五五将棋のオンライン対戦（4.4節・6.1節）と同じ運用方針（ルーム一覧＋番号参加、公開/非公開、名前任意、3時間TTL）を踏襲し、以下を実装した。

- Firestoreのコレクションは`tictactoeGames`を使用。
- ルーム作成時に**作成者が先手（○）/後手（×）を選択**できる（五目並べ・五五将棋で確立した仕組みをそのまま採用）。
- 決着理由（`winReason`）として「3並び」「投了」を管理し、結果バナーのメッセージを出し分ける。

## 8. ゲーム4: オートリオ

`Docs/todo.md`の要望により追加。実在のボードゲーム「Otrio」の**基本ルールのみ**を実装し、マスタールール（異サイズ混在の3並び）は実装していない。

- 3×3盤。各マスには小・中・大のサイズごとに駒を1つずつ重ねて置ける（既に置かれた駒は取り除かれない）。各プレイヤーは小・中・大の駒を3個ずつ、計9個保有する。
- 勝利条件: (1) 同じサイズの駒が縦・横・斜めのいずれかに3つ並ぶ、(2) 1つのマスに自分の小・中・大の駒がすべて揃う（トリオ）。異サイズ混在の3並びは勝利条件に含めない。
- 両者の持ち駒（18個）をすべて使い切っても決着しなければ引き分け。
- プレイヤーは1P（先手）固定、CPUは2P（後手）固定。
- 難易度ごとのAI実装:
  - **弱**: 即勝ちできる手を優先。なければ相手の即勝ち手を検出し、同じマス・サイズに打てるなら阻止。それ以外はランダム。
  - **中**: 深さ2のミニマックス＋評価関数（ライン・トリオそれぞれの完成度をスコア化）。
  - **強**: 深さ6・候補手上位10手に絞ったミニマックス＋αβ枝刈り（同じ評価関数を使用）。
- 画面構成: 盤面（3×3、各マスに小中大の入れ子表示）、自分/CPUの持ち駒表示、持ち駒を選択してから盤面をクリックして着手する操作方式（五五将棋の持ち駒選択と同じ操作パターン）。
- 投了ボタン・ルール説明画面あり。

### 8.1 オンライン対戦

〇×ゲーム（7.1節）と同じ運用方針で実装した。

- Firestoreのコレクションは`otrioGames`を使用。盤面に加え、持ち駒（`inventory`）もFirestoreに同期する。
- ルーム作成時に**作成者が1P（先攻）/2P（後攻）を選択**できる。
- 決着理由（`winReason`）として「勝利（同サイズ3並び／トリオいずれか、メッセージ上は区別しない）」「投了」「引き分け」を管理する。

## 9. ゲーム5: 四目並べ

`Docs/todo-feature.md`の要望「五目並べと同じルールでいいので、別ゲームとして四目並べを作って」により追加。ユーザーへの確認で「五目並べと同じ自由配置・盤面サイズも同程度」を選択したため、五目並べと全く同じ15×15自由配置ルールのまま、勝利条件のみ5連→4連に変更した（重力落下式のいわゆる「コネクトフォー」ではない）。

- 難易度ごとのAI実装: 五目並べのAI（弱=即勝ち即阻止+ランダム、中=パターン評価の貪欲法、強=ミニマックス+αβ枝刈り）をそのまま踏襲し、パターン評価の点数配分を4連基準に1段階シフトしただけ。

- 投了ボタン・ルール説明画面あり。

## 10. ゲーム6: ゴブレット・ゴブラーズ

`Docs/todo-feature.md`の要望「ゴブレット・ゴブラーズぽい概念のゲームを新しく作って」により追加。実在のボードゲーム「Gobblet Gobblers」の本家ルール（駒を被せる・盤上の駒を動かす）を実装した。オートリオ（同一マスに全サイズの駒が共存し、被せ合わない）とは異なるメカニクス。

- 3×3盤。各プレイヤーは小・中・大の駒を2個ずつ、合計6個持つ。手番には「持ち駒を新しく置く」か「盤上の自分の駒を動かす」のいずれかを行う。
- **被せるルール**: 駒は空いているマスだけでなく、自分より小さい駒（相手のものでも自分のものでも可）の上にも被せて置ける。被せられた駒はその場に残ったまま隠れる。
- **移動するルール**: 盤上にある自分の駒（一番上に見えている駒）は、空いているマスか自分より小さい駒の上へ動かせる。移動元に他の駒が隠れていれば、動かすと再び見えるようになる。
- 勝利条件: 一番上に見えている自分の駒が、縦・横・斜めのいずれかに3つ並ぶこと（駒のサイズが揃っている必要はない）。
- 引き分け: 同一局面（盤面+持ち駒+手番）が3回出現したら引き分けとする。これは本家ルールには存在しない実装上のセーフガードで、駒を動かし続けるだけで理論上は対局が終わらなくなり得るため、五五将棋の千日手判定と同じ考え方で追加した。
- プレイヤーは1P（先手）固定、CPUは2P（後手）固定。
- 難易度ごとのAI実装:
  - **弱**: 自分が勝てる手（新規配置・移動どちらも含む）があれば必打。相手が次に勝ってしまう手があれば、同じマスを自分の駒で埋められるなら阻止。それ以外はランダム。
  - **中**: 深さ2のネガマックス＋評価関数（ラインごとの「相手に阻害されていない自分の駒数」をスコア化）。
  - **強**: 深さ4・評価値上位12手に絞ったネガマックス＋αβ枝刈り（配置＋移動で分岐数が多いため候補を絞る）。
- 画面構成: 盤面（3×3、一番上の駒のみ表示。被せる/被せられるを色とサイズで表現）、自分/CPUの持ち駒表示、持ち駒を選択して盤面をクリックすると新規配置、盤上の自分の駒をクリックすると選択され移動先候補がハイライトされる操作方式。
- CPU対戦・オンライン対戦（Firestoreコレクション: `gobbletGames`）とも最初から実装。決着理由（`winReason`）は「3並び」「投了」「同一局面の繰り返し」。盤面のFirestore保存は、各マスの駒スタック（最大3個）を固定長3要素の数値配列にエンコードし、9マス×3要素=27要素のフラット配列にする独自方式（詳細は`Docs/design.md`参照）。
- 投了ボタン・ルール説明画面あり。
